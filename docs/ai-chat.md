# Фіча: AI-чат з поясненням змін (Лабораторна 6, варіант А)

Розширення наявної функції «AI-команда» (R-14, R-15). Baseline і контрольні приклади: [evaluation.md](evaluation.md).

## 1. Дія і користь

Користувач пише запит звичайною мовою у вкладці **AI** (чат). Застосунок змінює параметри (BPM, delay, reverb,
compressor, EQ) і відповідає повідомленням: **що змінено** (було → стало) і **навіщо** (коротке пояснення
для звукоінженера-початківця).

Користь порівняно з baseline:
- працюють відносні команди («довше», «менше», «наполовину») і вимкнення (`reverb off`) — baseline 0/3;
- користувач бачить і розуміє зміни, а не технічний лог `✓ fx k=v` — baseline 0/5 пояснень;
- небезпечні значення обмежуються; збій мережі не маскується під успіх.

## 2. Маршрутизація (рішення)

**Правила відповідають лише на прості однозначні команди, усе інше йде в Gemini разом із поточним станом.**

Команда вважається простою, якщо після вилучення розпізнаних фрагментів і службових слів не лишається нічого:

| Фрагмент | Приклади | Дія |
|---|---|---|
| темп | `120 bpm`, `bpm 120`, `темп 120` | `bpm` |
| поділ delay | `delay 1/8`, `ділей 1/16` (лише 4, 8, 16) | `delay on=true division=N` |
| увімкнення / вимкнення | `reverb off`, `вимкни компресор`, `turn on eq`, `delay on` | `on=true/false` |

Службові слова: `and`, `і`, `та`, `,`, `add`, `set`, `turn`, `at`, `the`, `на`, `з`.
Будь-яке інше слово (`зроби`, `довшим`, `warmer`, `наполовину`) → запит іде в Gemini.

Приклади: E1 → правила; E5 (`reverb off`) → правила, `on=false`; E2, E3, E4 → Gemini.

## 4. Дані, що передаються в Gemini

| Передається | Навіщо |
|---|---|
| текст запиту | сама команда |
| стан: `bpm`; `delay{on,division,feedback,mix}`; `reverb{on,mix,size}`; `compressor{on,threshold,ratio}`; `eq{on,low,mid,high}` | щоб «довше», «менше», «вимкни» мали точку відліку |
| до 3 останніх реплік чату (запит + підсумок змін) | «поверни як було», «ще трохи» |

| **Не** передається | Чому |
|---|---|
| аудіозапис, рівні сигналу | AI не обробляє звук; великий обсяг і приватний вміст |
| назви та метадані проєктів з Library | можуть містити особисту інформацію, для задачі не потрібні |
| повна AI history з Room | лише 3 останні репліки: менше токенів і менше особистих даних |
| ідентифікатори пристрою, акаунта | не потрібні; App Check працює окремо |

## 5. Випадки без результату (що бачить користувач)

| Випадок | Повідомлення в чаті | Параметри |
|---|---|---|
| Порожній запит | кнопка Send неактивна | без змін |
| Запит не про звук («яка погода?») | відповідь моделі `reply`: «Я керую лише BPM і ефектами…» + приклади | без змін |
| Дія вже виконана («reverb off», коли він вимкнений) | «Reverb уже вимкнений — нічого не змінив» | без змін |
| Модель повернула невідому дію / невалідний JSON | «Не вдалося зрозуміти відповідь AI» + Retry | без змін (атомарно) |
| Немає мережі, команда не проста | «Немає мережі. Офлайн працюють прості команди: `120 bpm`, `reverb off`, `delay 1/8`» + Retry | без змін |
| Таймаут 20 с | «AI не відповів вчасно» + Retry | без змін |
| Помилка налаштування (App Check, квота, модель) | «Хмарний AI недоступний (налаштування). Прості команди працюють» + Retry вручну, без автоповторів | без змін |

## 6. Критерій якості і приймання (AC)

Набір: E1–E5 з [evaluation.md](evaluation.md), однаковий для «до» і «після». Хмарні приклади (E2–E4)
запускаються **по 3 рази**; приклад зараховано, якщо намір виконано щонайменше у 2 з 3.

| ID | Критерій | Baseline | Ціль |
|---|---|---|---|
| AC-1 | Намір виконано (з мережею) | 2/5 | **≥ 4/5**, з них E3, E4, E5 — 3/3 |
| AC-2 | Кожен змінений параметр має пояснення «навіщо» | 0/5 | **5/5** успішних відповідей |
| AC-3 | Список «що змінено» збігається з фактичним diff стану | — | **5/5** (unit-тест) |
| AC-4 | E1 і E5 виконуються правилами офлайн, без виклику хмари | E1 так, E5 ні | **2/2** (unit-тест) |
| AC-5 | Після застосування немає значень поза діапазоном (feedback 1.5 → 0.9 + попередження) | ні | **так** (unit-тест) |
| AC-6 | Порожній ввід, офлайн, помилка налаштування, таймаут → визначений стан, без падіння і вічного спінера | частково | **4/4** (тести з fake + скриншоти) |
| AC-7 | Регресія: тести Лаби 5 і `BaselineAiTest` зелені, E1 у старому блоці дає той самий лог | — | **так** |

Критерій «пояснення зрозуміле» неперевірний автоматично: оцінюється вручну за чек-листом
(згадано параметр, напрям зміни, причина одним реченням) і позначається в таблиці як ручна перевірка.

## 7. План реалізації (Етап 3)

### 7.1 Місце виконання AI

| Компонент | Де виконується | Чому |

| Обрізання, diff, текст «що змінено» | на пристрої | детерміновано, перевіряється unit-тестами, не залежить від моделі |

### 7.2 Потік даних

```
Вкладка AI (AiChatScreen)
   │  текст запиту
   ▼
AiChatViewModel ── стан: Loading (поле і Send вимкнені)
   │  prompt + FxState.from(engine) + 3 останні репліки
   ▼
[1] ПІДГОТОВКА ДАНИХ           AiRequestBuilder
   │  порожній → InvalidInput; trim; ≤ 500 символів; history.takeLast(3)
   ▼  AiRequest(prompt, state, history)
[2] МАРШРУТИЗАЦІЯ              HybridSource
   ├─ SimpleCommandParser розібрав повністю ──► JSON від правил (source = rules)
   └─ інакше ──► FirebaseSource ── withTimeout(20 с) ──► Gemini (responseSchema)
   │             помилка/таймаут → AiError (без підміни відповіддю правил)
   ▼  CommandReply(json, source)
[3] ПЕРЕТВОРЕННЯ РЕЗУЛЬТАТУ
   │  AiReplyParser:  JSON → List<PlannedAction(action, why)> + reply
   │  ActionClamp:    значення → діапазони, список попереджень
   ▼  AiPlan(actions, reply, warnings, source)
AiChatViewModel (main thread)
   │  before = FxState.from(engine)
   │  ActionExecutor.apply(engine, actions)      (L-04 виправлено)
   │  after  = FxState.from(engine)
   │  ChangeDiff(before, after) → List<Change(param, from, to)>
   │  ExplanationBuilder(changes, why, warnings, reply) → ChatMessage
   ▼
Стан Success / NoResult / Error(retryable) → повідомлення в чаті
   │
   └─► AI history (Room, наявна таблиця, source = "chat:rules" | "chat:cloud")
```

### 7.4 БД, фонові задачі, контракт

- **БД:** змін немає, міграція не потрібна (L-17). Команди чату пишуться в наявну AI history.
  Самі повідомлення чату живуть у `ViewModel` (до кінця процесу) — свідоме обмеження.
- **Фонові задачі:** немає. Запит інтерактивний, користувач чекає на відповідь; WorkManager не потрібен.
- **API-контракт:** додається розділ «Запит і відповідь чату»: вхід `{state, history, prompt}`,
  вихід `{actions:[{fx, ..., why}], reply}` за `responseSchema`.

### 7.5 Стани UI

| Стан | Коли | Що на екрані |
|---|---|---|
| Idle | старт / після відповіді | поле активне; Send активна, якщо текст не порожній |
| Loading | запит у роботі | «AI думає…», поле і Send вимкнені |
| Success | є хоча б одна фактична зміна | повідомлення: зміни (було → стало) + навіщо + попередження |
| NoResult | дій немає або нічого не змінилось | `reply` моделі або «нічого не змінено» |
| Error | `Network`, `Timeout`, `AiUnavailable`, `InvalidResponse` | текст помилки + Retry; вічного Loading немає |
