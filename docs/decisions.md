# Технічні рішення

Формат: рішення, причина, наслідки.

## D-01: Kotlin + Jetpack Compose
Сучасний стандарт Android, мінімум коду для інтерфейсу з нестандартним малюванням (осцилограф). Наслідок: потрібна Android Studio з підтримкою Compose.

## D-02: DSP на чистому Kotlin для POC, Oboe пізніше
Швидко перевірити ідею без налаштування NDK. Наслідок: підвищена затримка і ризик пауз GC, тому перенесення на C++ (Oboe) заплановане (R-25).

## D-03: Аудіоформат mono, 44.1 кГц, float
Спрощує DSP і малювання сигналу. Наслідок: немає стерео та панорами (L-05).

## D-04: AI повертає JSON-дії, а не керує звуком напряму
Надійно, перевіряється та однаково виконується з будь-якого джерела (правила, хмара). Наслідок: набір дій обмежений схемою в `Ai.SYSTEM`.

## D-05: Інтерфейс `CommandSource` і гібридне джерело
Незалежність від постачальника AI; правила працюють офлайн, безкоштовно й миттєво, а хмара лише для нерозпізнаних фраз. Наслідок: два способи розбору команд, які треба підтримувати узгодженими.

## D-06: Firebase AI Logic (Gemini) замість Claude API
Власник проєкту вирішив не використовувати Claude API. Firebase AI Logic не вимагає зберігати ключ моделі в додатку й інтегрується з App Check. Наслідок: потрібен налаштований Firebase-проєкт; Claude API з коду прибрано.

## D-07: Firebase замість власного backend на першому етапі
Authentication, Firestore і Cloud Storage закривають акаунти, метадані та файли без написання сервера. Аудіо зберігається в Storage, а не в Firestore (ліміт документа). Наслідок: власний REST API відкладено (api-contract.md, розділ 4).

## D-08: Ледача ініціалізація Firebase-моделі (`by lazy`)
Додаток раніше падав при старті без `google-services.json`. Тепер Firebase зачіпається лише при першому хмарному виклику.

## D-09: Master volume застосовується після ефектів, осцилограф показує вже змінений сигнал
Користувач чує і бачить одне й те саме. `View gain` осцилографа змінює лише відображення. Окремо від цього працює слайдер Volume у дБ.

## D-10: Єдиний «транспорт» семплера (курсор, loop A-B)
Замість кількох накладених голосів один відтворюваний голос із позицією, loop-маркерами та прив'язкою до сітки BPM. Простіше для редагування фрагмента; семпл не транспонується.

## D-11: Лінійна вертикальна вісь осцилографа
Логарифмічний (дБ) режим прибрано на прохання користувача: рівні відображаються окремо як Peak/RMS у dBFS і лініями сітки.

## D-12: Кільцевий буфер для Live-осцилографа з вирівнюванням по нулю
Стабільна картинка без блокувань між аудіо- та UI-потоками; ціна: вікно до 4096 семплів (~93 мс).

## D-13: Документація в `docs/` у корені репозиторію, діаграми Mermaid
Діаграми живуть поруч із кодом і рендеряться на GitHub.

## D-14: Аудіо в WAV 16 біт stereo у приватній папці додатка
Без втрат, відкривається будь-де, заголовок пишеться вручну без бібліотек. Приватна папка (`filesDir`) не потребує дозволів. Імʼя файлу це UUID, а не назва користувача, тому немає проблем із символами й дублікатами. Файл пишеться як stereo на вимогу власника проєкту: mono-сигнал подається в обидва канали (dual-mono), бо рушій і мікрофон поки mono (D-03). Читання приймає mono і stereo (stereo зводиться в mono усередненням), тож старі mono-файли відкриваються. Наслідок: файл удвічі більший (≈10,6 МБ/хв), невелика втрата точності проти float (L-16); справжнє stereo потребує змін рушія; публічний експорт відкладено (R-24).

## D-15: Room для метадані та історії AI
Структура збігається з плануваною моделлю Firestore, тож хмарна синхронізація стане наступним кроком, а не переписуванням. Нову залежність (Room, KSP) схвалив власник проєкту. Наслідок: `exportSchema=false` і версія 1 без міграцій (L-17).

## D-16: Зберігається сухий запис і параметри, а не оброблений звук
Налаштування ефектів можна змінити пізніше, а файл лишається малим. Оброблений результат вирішено робити окремим експортом (R-24, етап 3).

## D-17: Курсор і маркери передаються через `ViewState`
Стан осцилографа живе в `ScopePanel` (`remember`), тому для Save він копіюється у `ViewState`, а для Load повертається через параметр `restore` після того, як `ScopePanel` бачить новий масив семплів. Наслідок: два місця, що тримають ці значення; проблема зникне після переходу на `ViewModel`.
D-17 (доповнення): `ViewState` має поле `owner` (посилання на масив запису), щоб `ScopePanel` після перестворення відрізняв актуальний стан від застарілого.

## D-18: Library як вкладка (`TabRow`), без Navigation Compose
Список збережених записів на окремій вкладці, щоб він не займав місце на головному екрані. `TabRow` не додає залежностей. Наслідок: L-21.

## D-19 (реалізовано): «ViewModel не знає Engine. Дії застосовує колбек, який передає екран.»

## D-20: «Категорії помилок AiError замість рядків; типи Firebase SDK не імпортуються поза FirebaseSource. Невпізнані винятки це Unknown.»

## D-21: «Ручний DI (AppContainer у App) замість Hilt: один сценарій, три залежності, нуль нових бібліотек. Hilt пояснюється на захисті як альтернатива, що автоматизує те саме створення об'єктів.». «Параметр конструктора AppContainer названо initialUseFake, бо однойменний параметр затінював властивість в ініціалізаторі й ламав перемикач; виявлено тестом container_switchesImplementationWithoutTouchingCallers»

## D-22: «FakeCommandSource лежить у main, бо потрібен debug-перемикачу.»

## D-23: «AiCommandViewModel створюється через by viewModels з фабрикою в MainActivity, залежності беруться з AppContainer. viewModel() з lifecycle-viewmodel-compose не використано, щоб не додавати залежність.»
